High Availability in Practice

Building, breaking, and recovering a Redis cluster — with Docker, three sentinels, and a deliberate failure.

What is Redis Sentinel?

Redis is fast, powerful, and widely loved — but a single Redis instance is a single point of failure. Redis Sentinel is the official solution for high availability: a distributed system that monitors your Redis master, automatically promotes a replica when the master goes down, and reconfigures all clients to use the new master.

In this lab, we'll set up a full Sentinel cluster from scratch using Docker Compose — one master, two replicas, three sentinels — and then deliberately kill the master to watch the automatic failover happen in real time.

💡
Sentinel requires a quorum — a minimum number of sentinels that must agree the master is down before triggering failover. We'll use a quorum of 2 out of 3, which means the cluster tolerates one sentinel going offline.

Redis Master Config

Minimal — just bind to all interfaces, disable protected mode so containers can reach each other.

redis-master/redis.conf conf
bind 0.0.0.0
port 6379
protected-mode no

Replica Config

Both replicas are identical — they point at redis-master by hostname. Docker's internal DNS resolves service names automatically.

  • redis-replica-1/redis.conf
  • redis-replica-2/redis.conf conf
bind 0.0.0.0
port 6379
protected-mode no
replicaof redis-master 6379

Sentinel Config

Each sentinel runs on port 26379 and monitors the master named mymaster. The two critical directives — resolve-hostnames and announce-hostnames — are explained in the Gotchas section below.

sentinel-{1,2,3}/sentinel.conf conf
port 26379

# Resolve hostnames lazily — required for Docker (see Gotchas)
sentinel resolve-hostnames yes
sentinel announce-hostnames yes

# Monitor the master — quorum of 2 required to trigger failover
sentinel monitor mymaster redis-master 6379 2

# Mark master as down after 5s of no response
sentinel down-after-milliseconds mymaster 5000

# Failover must complete within 10s
sentinel failover-timeout mymaster 10000

# Only sync 1 replica at a time during failover
sentinel parallel-syncs mymaster 1

Docker Compose

The master has a healthcheck so sentinels and replicas wait for it to be actually ready — not just started. Sentinels mount their entire directory (not just the file) so Redis can write temp files alongside the config.

docker-compose.yml yaml
services:

  redis-master:
    image: redis:7
    container_name: redis-master
    command: redis-server /usr/local/etc/redis/redis.conf
    volumes:
      - ./redis-master/redis.conf:/usr/local/etc/redis/redis.conf
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [redisnet]

  redis-replica-1:
    image: redis:7
    command: redis-server /usr/local/etc/redis/redis.conf
    volumes:
      - ./redis-replica-1/redis.conf:/usr/local/etc/redis/redis.conf
    depends_on:
      redis-master: { condition: service_healthy }
    networks: [redisnet]

    # redis-replica-2: same as above

  sentinel-1:
    image: redis:7
    command: redis-sentinel /sentinel-data/sentinel.conf
    volumes:
      - ./sentinel-1:/sentinel-data  # Mount directory, not file!
    depends_on:
      redis-master: { condition: service_healthy }
    networks: [redisnet]

    # sentinel-2, sentinel-3: same pattern

networks:
  redisnet:
    driver: bridge
 

Two Gotchas That Bit Us

The setup isn't plug-and-play. Two bugs surfaced immediately — both specific to how Redis Sentinel behaves inside Docker. Here's what happened and why.

Bug #1 — Hostname Resolution at Startup

⛔ Problem
Can't resolve instance hostname 'redis-master'

sentinel-2 and sentinel-3 crashed on startup with a fatal config error. Redis Sentinel (pre-6.2 default) tries to resolve the master hostname to an IP synchronously at config load time. If Docker's internal DNS isn't ready for that container yet — race condition — it fails immediately and exits.

docker logs sentinel-2 log
*** FATAL CONFIG FILE ERROR (Redis 7.4.9) ***
Reading the configuration file, at line 2
>>> 'sentinel monitor mymaster redis-master 6379 2'
Can't resolve instance hostname.
✅ Fix
sentinel resolve-hostnames yes

This directive (introduced in Redis 6.2) tells Sentinel to keep hostnames as-is and resolve them lazily at connection time — not eagerly at startup. Pair it with announce-hostnames yes so sentinels advertise hostnames (not raw IPs) to each other when they discover peers.

Bug #2 — Config Rewrite Permission Error

 
WARNING: Sentinel was not able to save the new configuration on disk

Redis Sentinel rewrites its config file at runtime whenever it discovers new peers or a failover happens. It does this with an atomic rename: write a .tmp file, then rename() it over the original. Two issues hit us in sequence:


Attempt 1 — mount the file directly: The redis user inside the container couldn't write to the /usr/local/etc/redis/ directory (owned by root). Result: Permission denied.

Attempt 2 — mount the file to /tmp/sentinel.conf: The temp file could be created, but rename() across bind-mount boundaries is blocked by Linux. Result: Device or resource busy.
 
Fix
Mount the directory, not the file

By mounting ./sentinel-1:/sentinel-data (the whole directory), the redis process can create temp files in the same filesystem namespace as the config — making the atomic rename() work perfectly. Sentinel now logs "Sentinel new configuration saved on disk" on every update.

 

Simulating a Master Failure

With all six containers healthy, it's time to do what the whole setup is designed for: kill the master and watch the sentinels take over.

failure simulation bash
# 1. Write a key to the master before we kill it
docker exec redis-master redis-cli SET mykey "hello-before-failover"
#  → OK

# 2. Kill the master
docker stop redis-master

# 3. Watch sentinel-1 logs for the failover
docker logs -f sentinel-1

What Happened — Step by Step

 
+sdown — Subjective Down
sentinel-1 detects it can no longer reach redis-master after down-after-milliseconds (5 000 ms). It marks the master as Subjectively Down — its own local judgement only.
 
+odown — Objective Down
Sentinels gossip. All three agree the master is unreachable. Quorum reached: 3/2. The master is now Objectively Down — failover can begin.
 
+try-failover — Leader Election
Sentinels run a Raft-style vote to elect one leader responsible for orchestrating the failover. sentinel-3 wins the vote.
 
+switch-master — Promotion
sentinel-3 promotes redis-replica-2 (172.26.0.4) to master. It sends SLAVEOF NO ONE to the chosen replica, then broadcasts the new master address to all other sentinels.
 
Reconfiguration Complete
redis-replica-1 is automatically reconfigured to replicate from the new master. The old master is tracked as a downed slave, ready to rejoin as a replica if it comes back.
docker logs sentinel-1 (key lines) log
1:X # +sdown master mymaster redis-master 6379
1:X # +odown master mymaster redis-master 6379 #quorum 3/2
1:X # +new-epoch 1
1:X # +try-failover master mymaster redis-master 6379
1:X # +vote-for-leader af2e7ca8... 1
1:X # +config-update-from sentinel af2e7ca8... @ mymaster redis-master 6379
1:X # +switch-master mymaster redis-master 6379 172.26.0.4 6379
1:X * +slave slave 172.26.0.3:6379 172.26.0.3 6379 @ mymaster 172.26.0.4 6379
verify — new master and data bash
# Ask sentinel who the master is now
docker exec sentinel-1 redis-cli -p 26379 sentinel get-master-addr-by-name mymaster
# 172.26.0.4
# 6379

# Is our key still there on the new master?
docker exec sentinel-1 redis-cli -h 172.26.0.4 -p 6379 GET mykey
# "hello-before-failover"  ✓
✅
Data survived! The key written to the original master before the crash was already replicated to both replicas. When the replica was promoted, the data was already there — zero data loss.

// 06 — Recovery

Old Master Rejoins as Replica

The original master isn't gone forever. When we bring it back with docker start redis-master, Sentinel detects it coming online and automatically sends it a SLAVEOF command — pointing it at the new master.

No manual configuration. No human in the loop. After a brief sync period, the old master is just another replica, and the cluster has three replicas total.

verify recovery bash
docker start redis-master

# ~15 seconds later...

docker exec redis-master redis-cli info replication
# role:slave                      ← was master, now a replica
# master_host:172.26.0.4          ← following the new master
# master_link_status:up           ← sync complete

docker exec redis-master redis-cli GET mykey
# "hello-before-failover"  ✓     ← data synced from new master

Key Takeaways

Quorum is the Core Mechanism

With 3 sentinels and quorum=2, the cluster tolerates 1 sentinel failure and still perform a reliable failover.

resolve-hostnames is Essential in Docker

Without it, sentinels fail at startup if Docker's DNS isn't ready for them — a silent but fatal race condition.

Mount Directories, Not Files

Sentinel rewrites its config atomically via rename(). Bind-mounting a single file breaks this — mount the directory instead.

Failover is Fast

With a 5s down-after-milliseconds, total failover completed in under 10 seconds — from master death to new master accepting writes.


Recovery is Automatic

Bring the old master back and Sentinel automatically demotes it — no manual SLAVEOF command needed.


Replication = Data Safety

Data written to the master before failure survives — because it was already replicated to the replicas before the crash.

 

Useful Sentinel Commands

sentinel CLI cheat sheet bash
# Who is the current master?
redis-cli -p 26379 sentinel get-master-addr-by-name mymaster

# Full master details (ip, port, flags, num-slaves, ...)
redis-cli -p 26379 sentinel masters

# List all replicas
redis-cli -p 26379 sentinel slaves mymaster

# List all sentinels known to this sentinel
redis-cli -p 26379 sentinel sentinels mymaster

# Trigger a manual failover (for testing)
redis-cli -p 26379 sentinel failover mymaster

# Check replication status on any node
redis-cli info replication
